# نظام نقاط البيع وإدارة المتجر (Retail POS)

نظام نقطة بيع وإدارة متجر باللغة العربية (RTL) مبني بـ Laravel 13 وFilament 5 وPostgreSQL 17،
مصمم لمتجر إكسسوارات ومستحضرات تجميل، ويصلح لأي متجر تجزئة.

يشمل: نقطة البيع بالباركود، المنتجات، المخزون ودفتر الحركات، الموردين والمشتريات والاستلام،
العملاء، البيع الآجل والذمم المدينة وكشوف الحساب وأعمار الديون، المرتجعات، الصندوق والمصروفات،
التقارير مع التصدير إلى Excel، سجل العمليات، وواجهة API جاهزة (`/api/v1`).

> النظام **ليس ERP**: لا يحتوي على موارد بشرية أو رواتب أو تصنيع أو محاسبة عامة كاملة.

## المتطلبات

| المكوّن | الإصدار |
|---|---|
| PHP | 8.4 أو أحدث، مع الإضافات: `pdo_pgsql`, `mbstring`, `intl`, `gd`, `zip`, `xml` |
| PostgreSQL | 17 (يُفضّل) — يحتاج إضافة `pg_trgm` (تأتي مع PostgreSQL) |
| Composer | 2.x |
| Node.js / npm | Node 20+ (لبناء ملفات الواجهة) |

لا يحتاج Docker.

## التثبيت

```bash
git clone <repo-url> retail-pos && cd retail-pos
composer install
cp .env.example .env
php artisan key:generate
```

أنشئ قاعدتي البيانات (التشغيل والاختبارات):

```bash
createdb retail_pos
createdb retail_pos_testing
```

عدّل بيانات الاتصال في `.env`:

```dotenv
DB_CONNECTION=pgsql
DB_HOST=127.0.0.1
DB_PORT=5432
DB_DATABASE=retail_pos
DB_USERNAME=postgres
DB_PASSWORD=كلمة_المرور
```

ثم أنشئ الجداول مع البيانات التجريبية، واربط مجلد الصور، وابنِ ملفات الواجهة:

```bash
php artisan migrate --seed
php artisan storage:link
npm install
npm run build
```

> بدون بيانات تجريبية (متجر حقيقي فارغ): شغّل
> `php artisan db:seed --class=Database\\Seeders\\ProductionSeeder`
> بدلًا من `--seed`، ثم غيّر كلمة مرور المدير فورًا.

## البنية

- **Services** (`app/Services`): كل منطق الأعمال. واجهة Filament والـ API تستدعيان الخدمات نفسها،
  والصلاحيات تُفحص داخل الخدمات وليس في الواجهة فقط.
  `SaleService`, `CustomerPaymentService`, `ReceivableService`, `ReturnService`, `InventoryService`,
  `PurchaseService`, `SupplierPaymentService`, `CashRegisterService`, `ExpenseService`,
  `CustomerStatementService`, `ReportService`, `DashboardService`.
- **دفاتر غير قابلة للتعديل**: `stock_movements`, `customer_ledger_entries`, `supplier_ledger_entries`,
  `cash_movements`. أي تصحيح يتم بحركة عكسية جديدة.
- **أرصدة مخزّنة يكتبها مصدر واحد فقط**: `products.stock_quantity` (InventoryService)،
  `customers.balance` (CustomerAccountService)، `suppliers.balance` (SupplierAccountService).
- **المال**: أعمدة `NUMERIC` فقط، والحساب بـ `brick/math` (فئة `App\Support\Money`) — لا `float`.
- **التزامن**: كل العمليات الحساسة داخل `DB::transaction()` مع `SELECT ... FOR UPDATE`،
  وتُقفل المنتجات بترتيب المعرّف لتفادي الـ deadlock.
- **حماية في قاعدة البيانات** (حتى لو تجاوز أحد الكود):
  - `balance_due = total - returned - paid + refunded` للفواتير.
  - رصيد العميل لا يكون سالبًا.
  - الكمية المرتجعة ≤ المباعة، والمستلمة ≤ المطلوبة.
  - صندوق مفتوح واحد لكل مستخدم ولكل صندوق.
  - باركود وSKU فريدان، وأرقام المستندات فريدة.
- **الترقيم**: جدول `document_sequences` مقفول أثناء الحجز؛ البادئات من الإعدادات (INV-, RCPT-, PO- …).

## قواعد الآجل والذمم

- البيع الآجل يتطلب عميلًا، ويُحسب تاريخ الاستحقاق من مدة سداد العميل (أو الافتراضي في الإعدادات).
- الحد الائتماني: `الدين الحالي + المبلغ الآجل الجديد ≤ الحد`. حد = 0 يعني لا بيع آجل.
  التجاوز يحتاج صلاحية «تجاوز الحد الائتماني» + تفعيله في الإعدادات، ويُسجَّل في سجل العمليات.
- الدفعة: لا تتجاوز دين العميل، توزَّع تلقائيًا على الأقدم استحقاقًا أو يدويًا (يجب أن يساوي مجموع التوزيع مبلغ الدفعة).
- لا تُحذف الدفعات: «عكس الدفعة» يعيد الدين ويُخرج النقد من الصندوق ويُسجَّل مع السبب.
- المرتجع يخفض المتبقي على الفاتورة أولًا ثم يُرد الباقي للعميل.

## الباركود

- **باركود الشركة المصنعة:** امسحه بالقارئ في حقل الباركود عند إنشاء المنتج، ويُقبل كما هو (EAN-13 أو UPC أو غيره).
- **باركود داخلي:** زر «توليد باركود» في نموذج المنتج أو صفحته، أو توليد جماعي من قائمة المنتجات.
  - الصيغة: 13 رقمًا تبدأ ببادئة الإعدادات (افتراضيًا `20`، وهو نطاق GS1 المخصص للاستخدام الداخلي، فلا يتعارض مع باركود أي شركة) + تسلسل + رقم تحقق، ويُطبع بترميز **Code 128** الذي تقرؤه كل قارئات USB الشائعة.
  - الفرادة مضمونة بثلاث طبقات: تسلسل مقفول، وتخطي القيم المستخدمة يدويًا، وفهرس فريد في قاعدة البيانات.
  - لا يُستبدل باركود موجود تلقائيًا أبدًا. تغييره أو إعادة توليده يحتاج صلاحية «إعادة توليد الباركود».
- **الملصقات:** زر «طباعة ملصقات الباركود» في صفحة المنتج والقائمة (طباعة جماعية أيضًا). المقاسات: 50×25، 40×30، 38×25، 58×40 مم للطابعات الحرارية، وورق A4 بـ24 أو 40 ملصقًا. يمكن إظهار/إخفاء السعر وSKU واسم المتجر من الإعدادات ← الباركود.
- اطبع الملصقات بمقياس 100% (بدون «ملاءمة للصفحة») حتى تبقى خطوط الباركود بعرضها الصحيح.

## طرق الدفع

| الطريقة | ما يُطلب من الكاشير |
|---|---|
| نقدي | — (يدخل الصندوق، مع حساب الباقي) |
| الحسابات | **نوع الحساب** (محفظة إلكترونية) + رقم المرجع إذا كان النوع يتطلبه |
| التحويلات البنكية | **رقم المرجع** (3 إلى 100 حرف). تُسجَّل الدفعة «بانتظار التأكيد» حتى يؤكدها مستخدم لديه صلاحية «تأكيد التحويلات البنكية» |
| آجل | العميل (مع الحد الائتماني وتاريخ الاستحقاق) |

- **تقسيم الدفع:** في نقطة البيع «+ تقسيم الدفع على أكثر من طريقة» (مثلًا جزء نقدًا وجزء بمحفظة). كل جزء يُحفظ كدفعة مستقلة. النقد فقط يدخل الصندوق، والباقي يُحسب على الجزء النقدي. في البيع الآجل تكون الأسطر دفعات مقدمة والباقي دَين.
- **أنواع الحسابات:** الإدارة ← أنواع الحسابات (المحافظ): إضافة، وتعديل الاسم، والتفعيل/التعطيل، واشتراط رقم المرجع، والإتاحة في نقطة البيع. القائمة الافتراضية من المحافظ المرخصة من البنك المركزي اليمني (تم التحقق في أكتوبر 2026): جوالي، جيب، كاش، ون كاش، محفظتي، فلوسك، إم فلوس. «جيبلي» مضاف **معطّلًا** لأنه لم يتم التحقق من وجود خدمة يمنية بهذا الاسم.
- **قواعد كل طريقة** (تتطلب نوع حساب / مرجعًا / تأكيدًا / متاحة في نقطة البيع) تُضبط من الإدارة ← طرق الدفع، ولا شيء منها مكتوب في الواجهة.
- **السجلات القديمة:** كل دفعة تحفظ اسم الطريقة ونوع الحساب كما كانا وقت الدفع، فإعادة التسمية لا تغيّر الفواتير القديمة.
- **رقم المرجع لا يثبت وصول التحويل.** راجع كشف البنك ثم استخدم «تأكيد وصول التحويل». تقرير «عمليات الحسابات والتحويلات» يعرض كل العمليات بأرقام مراجعها للمطابقة.

## النسخ الاحتياطي واستعادة قاعدة البيانات

الصفحة: **الإدارة ← النسخ الاحتياطي والاستعادة** (لمدير النظام فقط: صلاحيتا «إنشاء وتنزيل وحذف النسخ» و«استعادة قاعدة البيانات»).

### أين تُحفظ النسخ

- في المسار `BACKUP_PATH` في `.env`. اجعله **خارج مجلد التطبيق** حتى لا يحذفه تحديث التطبيق. إن تُرك فارغًا يُستخدم `storage/app/private/backups`.
- لا يوجد أي رابط عام للملفات: التنزيل فقط عبر النظام، لمستخدم مصرح، ومن مسار محفوظ في قاعدة البيانات. الملفات تُنشأ بصلاحية `600` والمجلد `700`.
- النسخ وكلمات المرور لا تُرفع إلى Git (المجلد خارج المشروع، و`.env` مستبعد).

### الأدوات المطلوبة

أدوات PostgreSQL للعميل: `pg_dump` و`pg_restore` و`psql`، بنفس الإصدار الرئيسي للخادم أو أحدث. إذا لم تكن في PATH (خصوصًا على Windows) حدّد مساراتها الكاملة:

```dotenv
PG_DUMP_PATH='C:\Program Files\PostgreSQL\17\bin\pg_dump.exe'
PG_RESTORE_PATH='C:\Program Files\PostgreSQL\17\bin\pg_restore.exe'
PSQL_PATH='C:\Program Files\PostgreSQL\17\bin\psql.exe'
BACKUP_PATH='D:\RetailPOS-Backups'
```

ضع مسارات Windows بين **علامات اقتباس مفردة** `'...'` (علامات الاقتباس المزدوجة تجعل `\` رمز هروب فيفشل قراءة `.env`).

كلمة مرور قاعدة البيانات تُمرَّر للأدوات عبر متغير البيئة `PGPASSWORD`، ولا تظهر في سطر الأوامر أو السجلات.

### ما تحتويه النسخة

- **قاعدة البيانات كاملة** بصيغة pg_dump custom: المنتجات، والتصنيفات، والمخزون وحركاته، والمبيعات وأصنافها، والعملاء، والدفعات وتوزيعاتها، والمرتجعات، والموردون والمشتريات، وحركات الصندوق، والمصروفات، والإعدادات، والمستخدمون والصلاحيات، وسجل العمليات.
- **الملفات خارج قاعدة البيانات** (صور المنتجات، والشعار) **ليست** جزءًا من قاعدة البيانات. عند تفعيل «تضمين صور المنتجات والشعار» (افتراضيًا مفعّل) تُنشأ بجانب كل نسخة ملف `...-files.zip` من `storage/app/public`، ويُنزَّل من زر «تنزيل الصور والملفات».
  - **استعادة الصور يدوية:** فك ضغط الملف داخل `storage/app/public` ثم شغّل `php artisan storage:link` إن لزم.
- الإيصالات وملفات PDF تُولَّد عند الطلب من البيانات، فلا تحتاج نسخًا.

### الاستعادة

1. اختر نسخة من القائمة، أو ارفع ملف `.dump` («رفع نسخة للاستعادة»). يُفحص الملف (توقيع PGDMP + `pg_restore --list` + وجود جداول المتجر)، ويُحفظ باسم يولّده النظام.
2. اضغط «استعادة» واكتب كلمة التأكيد **استعادة**.
3. يأخذ النظام **نسخة أمان تلقائية** من البيانات الحالية (نوع «نسخة أمان قبل الاستعادة»). إذا فشلت لا تتم الاستعادة.
4. تُمنع كل عمليات الكتابة على النظام أثناء الاستعادة.
5. يُستبدل المخطط `public` بمحتوى النسخة **في معاملة واحدة**: أي خطأ يلغي كل شيء وتبقى البيانات الحالية كما هي.
6. تُطبَّق الترحيلات الأحدث من النسخة (إضافية فقط، بدون `migrate:fresh`)، ثم يُتحقق من الجداول الأساسية، وتُسجَّل العملية في سجل العمليات وفي `storage/logs`.
7. قد تحتاج لتسجيل الدخول مجددًا بعدها (الجلسات جزء من قاعدة البيانات).

الاستعادة لا تلمس ملفات التطبيق، ولا `.env`، ولا الصور، ولا مجلد النسخ.

### النسخ التلقائي اليومي

1. فعّله من **الإعدادات ← النسخ الاحتياطي** (الوقت ومدة الاحتفاظ).
2. يجب أن يشغّل نظام التشغيل مجدول Laravel كل دقيقة:
   - **Linux** (`crontab -e`):
     ```
     * * * * * cd /path/to/retail-pos && php artisan schedule:run >> /dev/null 2>&1
     ```
   - **Windows:** مهمة في «جدولة المهام» (Task Scheduler) تتكرر كل دقيقة وتشغّل:
     `php C:\RetailPOS\artisan schedule:run`
3. صفحة النسخ الاحتياطي تعرض حالة المجدول الفعلية (نبضة كل دقيقة). إذا لم يُضبط المجدول تظهر رسالة تنبيه، ولا يدّعي النظام أن النسخ التلقائي يعمل.

النسخ المجدولة ونسخ الأمان الأقدم من مدة الاحتفاظ تُحذف تلقائيًا. **النسخ اليدوية لا تُحذف إلا يدويًا.** يمكن أيضًا تشغيل نسخة من الطرفية: `php artisan backup:run`.

### اختبار تكامل حقيقي

يُنشئ قاعدة معزولة باسم `retail_pos_backup_it`، ثم ينسخها ويغيّر بياناتها ويستعيدها ويتحقق منها، ثم يحذفها:

```bash
RUN_BACKUP_INTEGRATION=1 php artisan test --filter=BackupIntegrationTest
```

## نسخة سطح المكتب لـ Windows

مثبّت واحد `RetailPOS-Setup.exe` (Windows 10/11 x64) يحتوي كل ما يلزم: Electron وPHP 8.4 وPostgreSQL 17 والتطبيق في وضع الإنتاج. يعمل على `127.0.0.1` فقط، وتُحفظ البيانات (قاعدة البيانات والنسخ و`.env`) في `C:\ProgramData\RetailPOS` خارج مجلد التثبيت. لا يحذف التحديث ولا إلغاء التثبيت قاعدة البيانات، ويُنشأ قبل أي ترحيل في التحديث نسخة أمان (`pre_upgrade`) يتم التحقق منها.

البناء (على Linux، من الكود الملتزَم في git):

```bash
packaging/windows/build.sh
```

الناتج: `dist/RetailPOS-Setup.exe` و`dist/RetailPOS-Setup.exe.sha256`. نسخ المكوّنات وبصماتها مثبّتة في `packaging/windows/versions.env`.

دليل النقل والتثبيت والإعداد الأول والإبلاغ عن الأخطاء، مع قائمة اختبار على Windows: [packaging/windows/دليل-التثبيت-على-Windows.md](packaging/windows/دليل-التثبيت-على-Windows.md).

## API

المصادقة عبر Sanctum:

```bash
curl -X POST http://localhost:8000/api/v1/auth/token \
  -H "Accept: application/json" \
  -d email=cashier@pos.test -d password=password -d device_name=tablet
```

ثم أرسل الرمز في `Authorization: Bearer <token>`.

| الطريقة | المسار | الوصف |
|---|---|---|
| POST / DELETE | `/api/v1/auth/token` | إصدار / إلغاء رمز |
| GET | `/api/v1/me` | المستخدم وصلاحياته |
| GET | `/api/v1/products?search=` | المنتجات (مع ترقيم صفحات) |
| GET | `/api/v1/products/code/{barcode}` | بحث بالباركود أو SKU |
| GET | `/api/v1/customers`, `/customers/{id}` | العملاء |
| GET | `/api/v1/customers/{id}/statement` | كشف الحساب |
| POST | `/api/v1/customers/{id}/payments` | تسجيل دفعة |
| GET / POST | `/api/v1/sales` | المبيعات / إنشاء بيع |
| GET | `/api/v1/sales/{id}` | تفاصيل فاتورة |

حد الطلبات: 120 طلب/دقيقة للمستخدم، و5 محاولات دخول/دقيقة.
